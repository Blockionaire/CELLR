# WI-03 — Scan-to-catalogue resolver · PASS on programmed readings (behind `scan_resolver`, off by default) · real labels PENDING

Date: 2026-11-13 · Base: WI-02 checkpoint

## 1. What changed for a person (with `scan_resolver` on)

Nothing they have to learn. A scanned label is matched as before, by the same rules, and the review now says **why**
each wine is offered ("Precies deze naam in de CELLR-catalogus", "Een andere botteling met een vergelijkbare naam",
"Je eigen wijn, met een vergelijkbare naam") and shows the colour next to the place, so two near twins can be told
apart at a glance. "Niet deze" still leads to the editable form.

What changed underneath is where the candidates come from.

## 2. What changed

| Before                                                                                            | With `scan_resolver`                                                                                                                                           |
| ------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `matchLabel(facts, wines())`: **every** wine the household can see, catalogue included, in memory | `matchLabel` over a **bounded** set: the household's own wines, the wines of exactly that producer (≤ 40, indexed equality), the 20 best catalogue-search hits |
| A remembered photo loaded every wine to find one by id                                            | one lookup by id, under the person's row-level security                                                                                                        |
| No explanation                                                                                    | `resolution: { status, reasons }` on the scan result                                                                                                           |

| File                                                                 | Change                                                                                                                                                     |
| -------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `packages/domain/src/wine-resolver.ts`                               | `resolveWine(facts, candidates)`: status `exact_candidate` / `ambiguous` / `not_found`, candidates with reasons. The decision is `matchLabel`'s, unchanged |
| `apps/web/src/server/catalog/resolver.ts` (+ test)                   | Collects the bounded candidates through three existing read paths; drops every provider record; `null` when a lookup is not deployed                       |
| `apps/web/src/server/scans/service.ts` (+ tests)                     | Uses the resolver when wired; falls back to the old matching when it answers `null` or fails                                                               |
| `apps/web/src/server/cellar/repository.ts`                           | `listOwnWines`: the household's own wines only                                                                                                             |
| `apps/web/src/features/scan/scan-screen.tsx`, `messages/*.json`      | Reasons and colour per candidate; the batch re-match uses the server's candidates plus the household's own wines, never the whole catalogue                |
| `eval/scan/golden-resolver.json`, `scripts/scan-eval/golden.test.ts` | The golden set: 36 hand-written readings and 15 label texts against a deliberately confusable catalogue                                                    |
| `apps/web/e2e/scan-resolver.spec.ts`                                 | The pipeline end to end with the feature on                                                                                                                |

No migration: the resolver reads through `find_wines_by_label_text` and `catalog_search`, both merged earlier. Not
changed: client OCR, the photo cache, recognition from printed text, the vision call and its budget, image handling,
catalogue-learning signals, Koopcheck's photo path (still never stored).

### The lookup order, as built

1. The identical photo this household confirmed before (cache; no model). Unchanged.
2. Printed text naming exactly one catalogue wine (no model). Unchanged.
3. The vision model reads the label (the existing budget and rate limit). Unchanged.
4. **New:** the reading is resolved against the household's own wines + that producer's wines + the best search
   hits. The household's own wine is never passed over; a catalogue wine is "the one" only on an exact identity.
5. Records of external sources are **never** candidates here. Where a source is cleared for people, its records are
   offered by the search in the review's "search your wines", as suggestions the person confirms (WI-02).

Two confidences, never mixed: `facts.confidence` says how legible the label was; `matches[].score` and
`resolution.reasons` say how well a wine matches. A low-confidence reading of an exact name still matches exactly,
and the review still says the label was hard to read (golden case V35).

## 3. Golden evaluation (synthetic)

`eval/scan/golden-resolver.json`: expected answers written by hand from the rules in `docs/CATALOG.md`, before the
code was run against them. Every "read" is what a model _could_ return, every "text" what a phone's OCR _could_ read.
**None comes from a photograph.**

| Measure, on 36 hand-written readings                                         | Result                          |
| ---------------------------------------------------------------------------- | ------------------------------- |
| **Wrong automatic identity** (asserted exact, but not the expected wine)     | **0**                           |
| Asserted exactly one wine (auto-exact rate)                                  | 20 of 36 (all 20 expected ones) |
| Offered as a choice                                                          | 13                              |
| Nothing found                                                                | 2                               |
| Not a wine label                                                             | 1                               |
| Same answer whatever the order of candidates, with 200 unrelated wines added | yes (all 36)                    |

| Measure, on 15 hand-written label texts (no model)                                          | Result  |
| ------------------------------------------------------------------------------------------- | ------- |
| Resolved from the printed text alone                                                        | 7 of 15 |
| Wrongly resolved from text                                                                  | **0**   |
| Year: founding year and two years on a label left unknown; unknown never called non-vintage | yes     |

The set passed at its first run; no expected answer was changed afterwards. Covered: exact and alias; capitals and
missing accents; a hyphen read as a space; OCR-style 0/O and 1/l (offered, never asserted); Crianza / Reserva / Gran
Reserva; second wine and grand vin; two producers sharing a surname; red read as white; the same words from another
country; NV, a declared vintage, an unread year, a year of 2087; the household's own wine against a same-named
catalogue wine; only the estate read; the estate in the wrong field; a generic "Château"; an instruction printed on a
label; small print and brand text; a name over two lines.

"7 of 15 without a model" is the share on this hand-written set. It is **not** a forecast of the saving on real
bottles: curved, glossy and script labels often give no usable text (`RECOGNITION-ROADMAP.md`). The real figure is
what `/admin/ai` → recognition paths shows once people use it.

## 6. Known limits

- The scan screen still fetches `GET /api/v1/wines` (every visible wine) for the producer suggestions in the "new
  wine" form and for the fallback list. With the resolver on it is no longer used to decide which wine a label is.
  Removing it needs the bounded "recent wines" endpoint noted in WI-02.
- A third, merely similar wine of the same producer can appear next to two exact candidates (up to three are shown,
  as before). The reasons say which is which.
