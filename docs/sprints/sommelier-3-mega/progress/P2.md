## 4. Cost estimate and the spending guard for the paid baseline (nothing sent)

`pnpm sommelier:eval --engine v1-ai --estimate --set <set> --needs pairing,facts`. The estimate builds the prompts
with the app's own code and counts them. It prints two numbers:

- the platform's high estimate (`estimateCost`: about 3 characters a token, the full output allowance, two
  attempts);
- the reservations a run for real would hold back before each call (`reservationFor`, below).

It sends nothing and never opens or creates a budget file.

| Set                  | Calls | Tokens in / out (high) | High estimate per run | Reserved per run, call by call |
| -------------------- | ----: | ---------------------: | --------------------: | -----------------------------: |
| main (133 attempted) |   131 |      340,592 / 117,900 |               $0.2031 |                        $0.3337 |
| holdout-dev          |    45 |       105,293 / 40,500 |               $0.0668 |                        $0.1091 |
| holdout-test (blind) |    43 |       102,134 / 38,700 |               $0.0643 |                        $0.1050 |
| **All three**        |   219 |                        |           **$0.3342** |                    **$0.5478** |

### The guard: fail closed

A run for real (`--engine v1-ai`, with the owner's phrase and a key) works like this:

1. **It needs a budget file.** `--budget-file <path outside the repository> --total-usd <total>` is required.
   Without it, the engine is not built.
   - The file keeps what every run together has spent, and every run in it (`complete: false` until a run
     answered every scenario).
   - A file that cannot be read, that this tool did not write, or that holds another total is refused, never
     repaired.
2. **Each call is reserved first.** Before a call, `reservationFor` takes the most the call can cost:
   - every prompt character counts as half a token;
   - both attempts of the provider each use the full output allowance;
   - the repair's prompt also carries the first answer and the error (+400 tokens);
   - long-prompt rates apply when the input could reach them;
   - then 25% on top.
   - A model without a price, or a web-search call, is refused before anything is sent.
3. **It is sent only if the reservation fits.** The call goes out only when the reservation fits in what is left of
   the run's `--max-usd` **and** of the total, after earlier spend and any reservation still pending. Otherwise
   the run stops (`BudgetReached`) without sending.
4. **The reservation is on disk before the call.** It is written to the budget file before the call goes out, then
   replaced by the cost the provider reported.
   - A cost that was not reported (a timeout, an error, a thrown request) counts as the whole reservation.
   - A run that dies mid-call leaves its reservation counted. The owner clears it by hand, after checking the
     provider's usage page.
5. **A call that cost more than its reservation stops the run at once** (`callsOverReservation`). That happens with
   a dearer served model, or a price the list does not know.
6. **A stopped run is not a baseline.**
   - It prints `INCOMPLETE RUN`, exits with code 3, and is recorded as `complete: false`.
   - Its JSON and vectors say `incomplete: true`, and `compare` refuses incomplete vectors.
   - The scenario at which it stopped is not counted.

What the tests prove (`paid.test.ts`, no network):

- the reservation is at least the worst answer's cost as `pricing.ts` bills it;
- no call is sent whose reservation does not fit;
- a run stays under `--max-usd`;
- three runs together stay under `--total-usd`, even when each run's own limit is the whole total;
- the reservation is on disk before the call;
- unknown and thrown calls cost their reservation;
- an over-reservation stops the run;
- an unpriced model and a web search are refused;
- the paid engine needs a budget file;
- an estimate touches no budget file.

The CLI was also run three ways, with no key that works:

- with `--estimate` and a budget file: no file was created;
- without the phrase: refused, and no file was created;
- with the phrase but no budget file: refused before any call.

### Estimate against what the provider bills

The guard counts the cost of each call from the token usage the provider reports, priced with the app's own price
list (`pricing.ts`, `PRICING_VERSION`). That is close to the bill, not the bill itself:

- `pricing.ts` errs high. Uncached input is priced at the cache-write rate, and each call is rounded up to a whole
  micro-dollar.
- A price change by the provider after `PRICING_VERSION` would make the list wrong in either direction. The
  over-reservation stop catches a call that costs more than its reservation, but not a smaller drift.
- Nothing here reads the provider's invoice. After a paid run, the owner compares the budget file's `spentMicro`
  with the provider's usage page for the same hours.

In S9 the computed cost was $0.0961 for 1,095 calls. Whether the provider billed exactly that was not checked.

### Proposed baseline, to be approved (D-51)

V1 with AI, three runs of the three sets, with per-scenario vectors committed:

```bash
pnpm sommelier:eval --engine v1-ai --set <set> --needs pairing,facts --max-usd 0.60 --budget-file <outside>/v1plus-budget.json --total-usd 1.00 --vectors <outside>/<set>-<n>.json
```

- **Total: at most $1.00, enforced by the budget file.** Expected from S9's computed price: about $0.06 for all
  three runs.
- **Per run: `--max-usd 0.60`.** A whole run of the three sets reserves at most $0.55, so a run is stopped by its own
  limit only if its calls really cost close to their bounds.
- **Worst case:** if every call cost its full reservation, $1.00 covers about 1.8 runs. The third run would then stop,
  be marked incomplete, and not count. That is the guard working, not a baseline.
