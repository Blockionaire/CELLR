## 2. Variant E: the guard, bottle by bottle

The guard's one setting (the least confidence in the dish's reading at which it says anything) was chosen on the
**main set only**, and committed (`f1e7f07`, `GUARD_VERSION` 1) before either unseen set was run. "Medium" judged
40 more dishes than "high" at the same precision. Every wine of every pairing scenario's cellar was put to the guard
as if it had been offered (`guard-study.ts`; `results/s11-guard-study-*.json`):

| Set                        | Dishes judged | Good wines flagged | Acceptable flagged | Poor flagged    | Flags that were right |
| -------------------------- | ------------- | ------------------ | ------------------ | --------------- | --------------------- |
| main (developed on)        | 122 / 124     | 0 / 297            | 5 / 494 (1%)       | 757 / 2,321     | 99%                   |
| holdout-dev                | 43 / 45       | 0 / 123            | 0 / 231            | 103 / 437 (24%) | 100%                  |
| holdout-test (blind, once) | 37 / 43       | 0 / 68             | 0 / 132            | 274 / 504 (54%) | 100%                  |

Reading: when the guard objects it is right; it catches a quarter to a half of the poor wines (the rest are poor
without a hard clash: too light, too heavy, a mismatch the rules do not call a clash). The independent review found
that the first study read wines with their researched profile and the app's guard does not; the study was aligned
and re-run, with identical totals.

### 3.2 V1 with AI: what can be said without paying

V1 with AI offers about one bottle per answer and rarely a poor one. From S10's stored runs (mean of three):

| Set         | Bottles offered | Labelled poor |
| ----------- | --------------- | ------------- |
| main        | 117             | 5.0           |
| holdout-dev | 43              | 1.3           |
| blind half  | 36              | 2.3           |

So on the 88 unseen scenarios the guard has at most **about 3.6 poor bottles per run** to catch. If it catches them
at the rate of §2 (24–54%), that is one or two bottles per 88 answers. Its false-block rate on good and acceptable
wines was 0 of 554 on the unseen sets, so the expected cost is near nothing too. **This is an estimate**: it assumes the
poor bottles V1 picks are like poor bottles in general, which is likely optimistic (a model avoids the obvious
clashes the guard is built to catch). S10's stored runs keep no bottle names, so the exact number needs a new run.

### 3.3 The paid measurement (not run; needs the owner's approval)

`v1-ai` with the guard in shadow, three passes over main (133), holdout-dev (45) and the blind half (43), with
`--vectors` for paired comparison by dish. **Estimate: $0.33 per pass at the high bound** (`--estimate`; full output
allowance and one repair per call); S10's nine runs of the same engine cost **$0.067** in fact. Proposed cap: **$0.25**,
hard stop per invocation. Same model and settings as Production (`gpt-6-luna`, reasoning none), the key from the
environment's secret store, synthetic data only, labels and scorer unchanged, the guard frozen at version 1.

Decision rule, fixed now: the guard may be proposed for an active mode (a caution, `V1PLUS_ARCHITECTURE.md` §4) only
if on the unseen sets it flags **no** good or acceptable bottle of V1's and catches **at least one** poor one, and the
blind half does not go the other way. Otherwise it stays a shadow measurement, or is dropped.

### 3.4 Critical reading

- E is **safe but small**. Its ceiling on V1 with AI is a few percentage points of poor bottles, because V1 with AI
  already offers few. It is worth running in shadow because it costs nothing per answer, not because it will change
  the product.
- The larger measurable gain is elsewhere: when V1 has no model to ask, its plain answer is far worse than the
  engines' plan (§4.3). That is the fallback proposal in `V1PLUS_ARCHITECTURE.md` §5, not built.
- Removing a flagged bottle from a V1 answer is not safe (its text names the bottle), so "useful with flags applied"
  above is an upper bound, not what an active guard would show.

## 4. The statistical method (work package 5)

### 4.1 What S10 did

- **Repeated runs were not treated as independent.** Every interval used n = scenarios, with the runs averaged
  inside each scenario (`HYBRID_EVALUATION.md` §7; the analysis script's `paired()` and `summarise()`). The owner's
  concern is not what happened.
- **But scenarios were treated as independent, and they are not.** The 88 unseen scenarios are **44 dishes**
  (1–3 scenarios each, with different cellars). Two questions about one dish share most of what makes them easy or
  hard.
- §7.1's intervals were **Newcombe, unpaired**, on rounded run-averaged counts, while §6's decision rule named a
  **paired** bootstrap. The unpaired interval ignores that both engines answered the same scenarios, which usually
  makes it wider: conservative for the conclusion drawn (no activation).
- The per-bottle measures (poor bottles of all offered) were intervals over **bottles**, which are clustered in
  answers (an engine offering three bottles to one hard dish counts three times).
- holdout-dev is no longer fully unseen: since S9 its failures were read and rules answer to some of them
  (`sets.ts`). S10 reported it as unseen alongside the blind half.

### 4.2 What was built

`stats.ts`: each engine's runs are averaged within a scenario; the bootstrap draws **dishes** (every scenario of a
drawn dish goes in) and keeps both engines' values of a scenario together; a per-bottle measure is a ratio of sums over
the drawn scenarios; a resample with no bottle offered is left out and counted, never read as 0% poor; quantiles are
interpolated. `run.ts --vectors` writes per-scenario outcomes with the dish as cluster; for a blind set both are
salted hashes (`SOMMELIER_EVAL_BLIND_SALT`, random, never committed), the rows are sorted by key (in run order they
would line up with the scenario list), and the file must be outside every Git checkout, checked by real path.
`compare.ts` pairs files of one engine per side and says which scenarios it left out. Tests check that the same
answers run once or ten times give the same interval, and that 20 dishes asked twice give the interval of 20 dishes.

### 4.3 Checked against S10, and one free comparison

S10's stored holdout-dev runs, re-analysed with the new tool (paired, 45 scenarios of 22 dishes):

| Difference with A (V1 with AI) | By scenario (S10's method) | By dish (S11)  |
| ------------------------------ | -------------------------- | -------------- |
| D, first bottle                | −16 [−29, −4]              | −16 [−28, −4]  |
| D, no poor bottle              | −15 [−25, −6]              | −15 [−24, −7]  |
| C, first bottle                | −24 [−39, −10]             | −24 [−39, −10] |

The tool reproduces S10's numbers, and clustering by dish hardly moves them here (the scenarios of one dish use
different cellars). **S10's conclusion stands.** Future comparisons, and above all the human holdout (100 dishes asked
in two languages: 200 scenarios, 100 independent observations at most), must be clustered by dish.

Free comparison, the engines' plan (B) against V1 **without** AI (one run each; deterministic):

| Set (dishes)      | First bottle   | No poor bottle | Useful answer  |
| ----------------- | -------------- | -------------- | -------------- |
| main (100)        | +46 [+36, +56] | +75 [+67, +83] | +73 [+64, +81] |
| holdout-dev (22)  | +20 [+0, +38]  | +67 [+53, +79] | +58 [+41, +73] |
| holdout-test (22) | +35 [+16, +55] | +63 [+45, +78] | +53 [+38, +69] |

### 4.4 What the intervals still do not cover

The scenarios are one AI's idea of dishes, labelled by an AI. An interval says how far the result could move with
other scenarios of the same kind, not how real people's dishes go. That is what the human holdout is for.
